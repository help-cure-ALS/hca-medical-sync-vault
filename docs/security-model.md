# Security Model

TENOS Sync Vault is designed as a zero-knowledge transport and backup service for encrypted medical data.

## Primary Security Goals

- The server never sees medical plaintext.
- The server never stores medical encryption keys.
- A leaked subject ID is not enough to obtain sync access.
- Device access can be revoked server-side.
- Recipient devices can write encrypted data without gaining owner privileges.
- Operational statistics do not reveal identifiers or payloads.

## Non-Goals

- User identity management.
- Password authentication.
- Medical record querying.
- Server-side FHIR interpretation.
- Server-side consent decisions beyond transport authorization.

## Trust Boundaries

### Mobile App

Trusted for:

- Holding medical encryption keys.
- Holding Ed25519 private keys.
- Encrypting and decrypting payloads.
- Applying medical data semantics.
- Presenting consent and sharing UX.

### Sync Vault

Trusted for:

- Storing ciphertext durably.
- Verifying proof-of-possession signatures.
- Enforcing device status and capabilities.
- Enforcing quotas and rate limits.
- Serving aggregate operational statistics.

Not trusted with:

- Medical plaintext.
- Patient identity data.
- Medical encryption keys.

## Subject IDs

`subject_id` is a random UUID generated by the app. It is an anonymous data scope, not an identity claim.

Knowing a `subject_id` does not allow a client to register a different key, mint a JWT, push events, pull events, or delete the subject.

## Proof-of-Possession

JWT issuance requires signing a short-lived challenge.

Owner devices sign with the subject root private key.

Recipient devices sign with their own device private key after the owner has granted that device through `/devices/authorize`.

## Device Capabilities

Current capabilities:

| Capability | Can pull | Can push | Owner-only actions |
| --- | --- | --- | --- |
| `owner` | Yes | Yes | Yes |
| `read_write` | Yes | Yes | No |

Owner-only actions:

- disabling another device
- hard-deleting a subject
- rotating the subject root key

## Revocation

Device-level revocation is represented by `devices.status = 'disabled'`.

Subject-wide JWT invalidation is represented by `subjects.token_version`. Existing JWTs become invalid when their `tv` claim no longer equals the database value.

Subject hard-delete removes encrypted events and the subject row. Device and challenge rows are removed through cascading deletes.

## Encrypted Events

Events are stored as:

- metadata required for sync
- nonce
- ciphertext
- ciphertext hash

The server cannot inspect the encrypted medical payload. Logging must never include payload contents, private keys, JWTs, app tokens, admin tokens, or bundle-cipher secrets.

## Bundle-Cipher Bootstrap

Bundle-cipher material is fetched at runtime through app-token protected endpoints. The server derives a NaCl `secretbox` key from configured server-side secrets via HKDF.

This mechanism moves bundle-cipher material out of mobile build-time environment variables, but it is still a bootstrap channel and must not be confused with medical record encryption.

## Admin Statistics

`GET /admin/stats/summary` is protected by a server-only bearer token.

It returns aggregate operational counts only and must not expose:

- subject IDs
- device IDs
- public keys
- JWTs
- app tokens
- admin tokens
- bundle-cipher secrets
- event payloads

## Operational Rules

- Keep `.env` private.
- Use long random secrets in production.
- Do not expose the API container directly in production.
- Store PostgreSQL backups encrypted and off-server.
- Treat backups as sensitive because they contain ciphertext, subject metadata, device metadata, and sync state.
- Do not include production identifiers or secrets in public issues.
- Rotate secrets if they were committed, logged, screenshotted, or shared outside trusted channels.
