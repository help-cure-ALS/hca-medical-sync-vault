# Architecture

TENOS Sync Vault is a zero-knowledge sync backend for encrypted medical app data. It stores append-only ciphertext events and provides transport-level authorization, device management, quotas, and operational statistics.

The application layer remains responsible for medical data models, encryption, consent UX, and export behavior.

## System Overview

```text
Mobile app
  - creates subject and device IDs
  - owns medical encryption keys
  - owns Ed25519 signing keys
  - encrypts payloads before upload
        |
        | HTTPS, ciphertext only
        v
Fastify API
  - app-token guard for pre-auth endpoints
  - Ed25519 proof-of-possession
  - JWT capability verification
  - device registry and capabilities
  - quotas and rate limits
        |
        v
PostgreSQL
  - subjects
  - devices
  - events
  - auth_challenges
  - rendezvous
```

## Core Concepts

### Subject

A subject is an anonymous data scope. It is represented by a random UUID generated by the client app.

A subject is not a user account and does not contain identity data such as name, email, date of birth, diagnosis, or address.

The `subjects.public_key` column stores the subject root Ed25519 public key. The corresponding private key stays on owner devices.

### Device

A device is a registered sync participant for one subject.

Owner devices have `devices.public_key = NULL` and authenticate against the subject root key.

Recipient devices have their own Ed25519 public key in `devices.public_key` and authenticate against that device key.

### Capability

Device access is represented by `devices.capability`.

Current values:

- `owner`: owner device, authenticated by the subject root key.
- `read_write`: recipient device, authenticated by its own device key.

`read_write` devices may push encrypted events and pull encrypted events. They cannot perform owner-only operations such as disabling other devices, deleting the subject, or rotating the subject root key.

### Event

An event is an encrypted append-only sync record.

The server stores:

- routing and ordering metadata
- ciphertext algorithm label
- nonce
- ciphertext
- ciphertext hash

The server does not decrypt the ciphertext and does not know the FHIR resource contents.

## Authentication Flow

### 1. Subject Registration

`POST /subjects/register`

The client sends:

- `subject_id`
- `public_key_b64`
- `signature_b64`

The signature is verified against a deterministic registration message:

```text
register|<subject_id>|<public_key_b64>
```

If the subject already exists, the public key must match. Re-registering the same subject with a different key is rejected.

### 2. Challenge

`POST /auth/challenge`

The client sends:

- `subject_id`
- `device_id`

The server stores a random 32-byte challenge with a short TTL and returns:

- `challenge_id`
- `challenge_b64`
- `expires_in`

Only one unused challenge per subject/device pair is kept.

### 3. Issue JWT

`POST /auth/issue`

The client signs:

```text
issue|<subject_id>|<device_id>|<challenge_id>|<challenge_b64>
```

For owner devices, the server verifies the signature with `subjects.public_key`.

For recipient devices, the server normally verifies with `devices.public_key`. If a request for an existing device is signed by the subject root key, the server treats it as an owner reclaim and converts the device row back to owner.

The issued JWT contains:

- `sub`: subject ID
- `scope`: `sync`
- `device_id`
- `tv`: token version
- standard issuer, audience, issued-at, expiry, and JWT ID claims

## Authorization Enforcement

Authenticated endpoints verify:

- JWT signature and issuer/audience.
- Subject exists.
- Subject is not disabled.
- JWT `tv` equals `subjects.token_version`.
- Device exists for the subject.
- Device status is `active`.
- Device capability is sufficient for the operation.

Owner-only operations:

- disable another device
- hard-delete a subject
- update the subject root key

Writable operations:

- owner devices
- `read_write` recipient devices

## Pairing Mailbox

The `rendezvous` table is a short-lived pre-auth mailbox for pairing.

It stores only public material and ciphertext required for pairing. It must not contain medical plaintext.

Slots:

- `offer`
- `reply`

When a `reply` is fetched, all slots for that token are deleted.

## Cursor Model

Event pulls use a stable cursor based on:

```text
(server_received_at, event_id)
```

The timestamp is formatted in SQL as a UTC ISO string with millisecond precision. Clients must reuse the returned cursor values directly.

## Quotas

Subjects have default total and daily quotas:

| Limit | Default |
| --- | ---: |
| Total events | 5,000,000 |
| Total encrypted bytes | 500,000,000 |
| Daily events | 20,000 |
| Daily encrypted bytes | 50,000,000 |

Only actually inserted events count toward quotas. Duplicate `event_id` writes are idempotently acknowledged and do not increment counters.

## Admin Statistics

`GET /admin/stats/summary` returns aggregate operational statistics.

It is protected by `Authorization: Bearer <ADMIN_STATS_TOKEN>` and is separate from app JWT authentication.

The response does not include subject IDs, device IDs, public keys, JWTs, app tokens, admin tokens, bundle-cipher secrets, or event payloads.

## Database Tables

### `subjects`

Stores the anonymous subject scope, root public key, token version, disable state, quota limits, and quota counters.

### `devices`

Stores devices per subject, status, optional recipient public key, capability, creation time, and last seen time.

### `events`

Stores append-only encrypted events with metadata required for idempotency, ordering, and pull cursors.

### `auth_challenges`

Stores short-lived proof-of-possession challenges.

### `rendezvous`

Stores short-lived pairing mailbox payloads.
